# `trel` — adding joins (v1.5)

## Context

`trel` v1 is complete and on `main`: a relational-algebra TS query library
for Postgres with `project / where / order / limit / offset`, an introspection
CLI, and a node-postgres executor. The v1 plan deliberately deferred joins
but designed for them: every `TableRef` is always aliased
(`src/ast/relation.ts:17`), every `ColumnRef` is always qualified by alias
(`src/ast/expression.ts:13`), and the SQL serialiser uses a "collect clauses,
then emit one canonical SELECT" pattern (`src/sql/serialise.ts:34`) that can
absorb a JOIN list cleanly.

The next increment is **`INNER JOIN` only**:

```ts
const rows = await db.run(
  users
    .innerJoin(posts)
    .on(users.id.eq(posts.authorId))
    .where(posts.body.isNotNull())
    .project(users.email, posts.body.as("post")),
);
```

`LEFT / RIGHT / FULL` joins are deferred to a follow-up; they introduce
nullability widening on one side, which is the interesting half of the type
machinery and warrants its own iteration.

## Decisions

- **Scope:** `INNER JOIN` only this round.
- **Column-name collisions** on the merged columns shape produce a **compile
  error**. Users must `.project(...)` to disambiguate, or wait for table
  aliasing (`.as("u")`) in a future iteration.
- **No merged accessors** on the joined relation — same as `.where(...)`
  already returns. Users reference columns via the original `users` / `posts`
  table objects, which are in scope.
- The JOIN syntax is two-step: `.innerJoin(other)` returns a `JoinBuilder`
  whose only method is `.on(predicate)`, which returns the joined `Relation`.
  This makes "forgot the ON clause" a compile error.

## Design

### AST

Add one variant to `RelationNode` (`src/ast/relation.ts`):

```ts
interface InnerJoin {
  kind: "innerJoin";
  source: RelationNode; // existing left side (may already carry where/order/...)
  right: TableRef; // joined-in table
  on: ExpressionNode; // join predicate
}
```

`source` keeps the existing `.source`-chain pattern, so `where / order /
limit / offset / project` can sit on top of a join unchanged. `right` is
restricted to `TableRef` for v1.5 — joining a sub-query is deferred.

Factory: `innerJoin(source, right, on): InnerJoin`. Pure, no validation.

### Serialiser

`collect()` in `src/sql/serialise.ts:59` currently assumes exactly one
`TableRef` and throws on more. Restructure `CollectedClauses` to hold:

```ts
type CollectedClauses = {
  primary: TableRef | null;
  joins: Array<{ kind: "inner"; right: TableRef; on: ExpressionNode }>;
  // ...projectionItems, predicates, orderTerms, limit, offset (unchanged)
};
```

In the recursive walk, `case "innerJoin"` pushes onto `joins` (in source-tree
order — same `unshift`-style trick used for predicates so chained joins emit
left-to-right) and recurses into `node.source`. The base-case `TableRef`
still sets `clauses.primary`.

`emitSelect()` (`src/sql/serialise.ts:94`) gets a new clause between FROM
and WHERE:

```sql
FROM "schema"."primary" "alias"
INNER JOIN "schema"."right" "ralias" ON <on-expr>
```

Each `on` expression is emitted via the existing `emitExpression`, so
parameter numbering remains left-to-right across the whole tree (joins ON
predicates first, then WHERE predicates, then anything inside Project).

No changes needed to `emitExpression` — `ColumnRef` already qualifies by
`tableAlias`.

### Fluent layer

Add to `Relation` (`src/query/Relation.ts`):

```ts
innerJoin<RColumns extends ColumnsShape>(
  right: Relation<RColumns> & { _tableName: string; _schema: string },
): JoinBuilder<Columns, RColumns>;
```

The constraint forces the argument to be a `defineTable(...)` result
(carries `_tableName` / `_schema`); a generic `Relation<...>` won't satisfy
it, which is what we want for v1.5.

New tiny class `JoinBuilder<L, R>` (one file, `src/query/JoinBuilder.ts`)
exposing only:

```ts
on(predicate: Expression<boolean>): Relation<MergedColumns<L, R>>;
```

It holds the left source node, the right `TableRef`, and constructs an
`InnerJoin` node when `.on(...)` is called.

### Type machinery

`MergedColumns<L, R>` (in `src/query/types.ts`):

```ts
type MergedColumns<L extends ColumnsShape, R extends ColumnsShape> =
  Extract<keyof L & keyof R, string> extends never
    ? Readonly<L & R>
    : {
        // Force a clear error when columns collide. Listing the offending
        // keys in the type makes the message useful.
        readonly __collision: `Joined tables share columns: ${Extract<keyof L & keyof R, string>}`;
      };
```

The collision branch resolves to a record without any of the methods that
downstream code expects on `ColumnsShape`, so passing it to `.where /
.project / db.run` produces a TS error pointing at the `__collision` field.
We tune the message in implementation if it's not legible enough.

Existing `ProjectableItem<Columns>` and `ComparableTo<Type>` work unchanged:
`.project(...)` accepts columns from either source because both sides'
columns are now in `Columns`; cross-table predicates already typecheck
because `ComparableTo` matches on TS type + SQL tag, not on table identity.

## Open questions / risks

- **`MergedColumns` error legibility.** `Readonly<L & R>` may produce
  TS-inferred types that are awkward to read in IDE tooltips. If the
  experience is poor, replace with a hand-written mapped type. Decide
  during implementation.
- **`right` restricted to `TableRef`.** Joining a sub-query
  (`users.innerJoin(otherRelation.where(...))`) is deferred. The fluent
  signature reflects this via the `_tableName` / `_schema` constraint on the
  argument; loosening later is purely additive.
- **Stacked-join parameter ordering.** Parameters across multiple ONs and a
  trailing WHERE must number left-to-right. Covered by an explicit
  serialiser test.

## Deferred (still post-v1)

- `LEFT / RIGHT / FULL OUTER` joins (next iteration) — requires a
  `NullableColumns<C>` type to widen the outer side's columns by `| null`.
- Table aliasing via `.as("u")` — solves collisions properly, allows
  self-joins, lets `right` be a renamed table.
- Joining sub-queries (drop the `_tableName`/`_schema` constraint on
  `innerJoin`'s argument).
- `USING (col)` shorthand.
- Aggregates + `group by` + `having`, set ops, CTEs, DML, transactions,
  streaming, migrations-based codegen — all unchanged from the v1 deferred
  list.
