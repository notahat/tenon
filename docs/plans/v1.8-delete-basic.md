# `tenon` — basic DELETE (v1.8)

## Context

`tenon` v1.7 shipped basic single-row INSERT with optional `RETURNING`.
The library can now read and insert; it cannot yet remove rows.

The next increment is **basic DELETE** with an optional `RETURNING`
clause, accessed Rails-style through a where-narrowed scope on the
target table:

```ts
// Standard path: predicate-narrowed DELETE.
await db.run(users.where(users.id.eq(42)).delete());
// -> { rowCount: number }

// Multiple predicates AND together.
await db.run(
  users
    .where(users.email.eq("pete@notahat.com"))
    .where(users.active.eq(true))
    .delete(),
);

// RETURNING produces typed rows, same shape machinery as Relation/Insert.
const removed = await db.run(
  users
    .where(users.id.eq(42))
    .delete()
    .returning(users.id, users.email),
);
//    ^? Array<{ id: number; email: string }>

// Explicit "wipe the whole table" — required for empty-WHERE.
await db.run(users.deleteAll());

// Bare `users.delete()` is callable but throws in the serialiser
// before a round-trip; the error message points at `deleteAll()`.
```

Decisions chosen by the user up-front:

- **Rails-style chain** — introduce a `DeletableScope` returned by
  `Table.where(...)` carrying `.where` (returning itself) and
  `.delete()`. `Table.delete()` exists too but trips the empty-WHERE
  guard.
- **Throw at runtime** if a `DeleteNode` reaches the serialiser with
  zero predicates and the explicit `allowEmptyPredicates` flag is
  off. `Table.deleteAll()` is the only path that flips the flag on.
- **Defer the Rails-style `Table.where(...).insert(attrs)` chain
  to v1.9.** The DELETE chain reuses `Relation`'s predicate
  machinery directly; the INSERT chain needs a separate
  predicate-to-attrs extractor and is its own iteration.

## Decisions

- **`Delete` is its own AST + class, not a `RelationNode` variant.**
  Same justification as `Insert` in v1.7: keeps the SELECT
  serialiser, the duplicate-column brand, and the join machinery
  free of "is this a relation?" guards.
- **`DeleteNode` stores predicates as a flat `ExpressionNode[]`,
  not a nested `Where(Where(...))` chain.** Predicates are AND-ed
  in user order at emit time. Conversion from the `Relation`-side
  nested form happens once, when `.delete()` is called on a
  `DeletableScope`.
- **Alias is preserved on emit** (unlike `Insert`). Postgres
  accepts `DELETE FROM "schema"."tbl" AS "u" WHERE "u"."id" = $1`,
  and column refs in our predicates are already qualified by the
  alias the user chose via `.as(...)` (or by the table name when
  unaliased). Reuse the existing `emitTableRef`.
- **Empty-WHERE guard lives in the serialiser, not the fluent
  layer.** `DeleteNode.allowEmptyPredicates: boolean` is the
  signal. `Table.delete()` produces `false`; `Table.deleteAll()`
  produces `true`. `emitDelete` throws on `predicates.length === 0
  && !allowEmptyPredicates` with a message pointing at
  `deleteAll`. This way every code path that reaches SQL is
  guarded, including any future internal AST construction.
- **`DeletableScope` extends `Relation<Columns>` and overrides
  `.where`** to keep returning `DeletableScope`. Other Relation
  operators (`.order`, `.limit`, `.project`, `.innerJoin`)
  inherited from `Relation` widen back to `Relation` and lose
  `.delete` — which is correct: DELETE has no ORDER/LIMIT/JOIN in
  this iteration. (Postgres supports `DELETE ... USING` and
  `RETURNING` only; ORDER/LIMIT are not part of DELETE syntax.)
- **`DeletableScope` carries the `TableRef` explicitly** rather
  than re-deriving it by walking the source chain at `.delete()`
  time. Cheaper and clearer; the scope is the only constructor
  call site for itself, so the invariant is local.
- **`DeleteNode.predicates` is built by walking the
  `DeletableScope`'s relation node back through its `Where`
  ancestors to the root `TableRef`.** A single helper
  (`collectWherePredicates`) handles this; it asserts the chain
  bottoms out at a `TableRef` (it always does, by construction).
- **No `Table.delete(predicate)` shortcut.** Only the chained form
  `Table.where(predicate).delete()`. One path, zero surface-area
  duplication.

## Design

### AST

New file `src/ast/delete.ts`:

```ts
import type { ExpressionNode } from "./expression.js";
import type { ProjectionItem, TableRef } from "./relation.js";

/**
 * A DELETE statement targeting a single base table. Predicates
 * are AND-ed in array order at emit time. `allowEmptyPredicates`
 * is the explicit "I really want to wipe the table" flag — set
 * only by `Table.deleteAll()`. The serialiser throws if the
 * predicate list is empty and the flag is off.
 */
export interface DeleteNode {
  readonly kind: "Delete";
  readonly target: TableRef;
  readonly predicates: readonly ExpressionNode[];
  readonly allowEmptyPredicates: boolean;
  readonly returning: readonly ProjectionItem[] | null;
}

export function deleteNode(args: {
  readonly target: TableRef;
  readonly predicates?: readonly ExpressionNode[];
  readonly allowEmptyPredicates?: boolean;
  readonly returning?: readonly ProjectionItem[] | null;
}): DeleteNode {
  return {
    kind: "Delete",
    target: args.target,
    predicates: args.predicates ?? [],
    allowEmptyPredicates: args.allowEmptyPredicates ?? false,
    returning: args.returning ?? null,
  };
}
```

`DeleteNode` is **not** a member of `RelationNode`. `relationToSql`
keeps its existing exhaustive switch.

### Serialiser

`src/sql/serialise.ts` — add a sibling top-level entry point. The
`EmitContext`, `emitTableRef`, `emitExpression`, and `emitSelectList`
helpers stay module-private; `emitPredicates` is also already
module-private and is reused as-is.

```ts
export function deleteToSql(node: DeleteNode): CompiledQuery {
  const context: EmitContext = { params: [] };
  const text = emitDelete(node, context);
  return { text, params: context.params };
}

function emitDelete(node: DeleteNode, context: EmitContext): string {
  if (node.predicates.length === 0 && !node.allowEmptyPredicates) {
    throw new Error(
      "DELETE without a WHERE clause is forbidden. " +
        "Call Table.deleteAll() if you really mean to wipe every row.",
    );
  }
  const target = emitTableRef(node.target);
  const where =
    node.predicates.length > 0
      ? ` WHERE ${emitPredicates(node.predicates, context)}`
      : "";
  const returning =
    node.returning === null
      ? ""
      : ` RETURNING ${emitSelectList(node.returning, context)}`;
  return `DELETE FROM ${target}${where}${returning}`;
}
```

Parameter numbering: WHERE first (left-to-right across the
flattened predicate list), then RETURNING — same canonical order
as INSERT.

### Fluent layer

New file `src/query/Delete.ts`:

```ts
export class Delete<
  Columns extends ColumnsShape,
  Returning extends ColumnsShape | null,
> {
  declare readonly _kind: "delete";
  declare readonly _columns: Columns;
  declare readonly _returning: Returning;

  constructor(readonly node: DeleteNode) {}

  /** Add or replace the RETURNING clause. */
  returning<const Items extends readonly ProjectableItem[]>(
    ...items: Items
  ): Delete<Columns, ProjectedShape<Items>> {
    const projectionItems = items.map(toProjectionItem);
    return new Delete<Columns, ProjectedShape<Items>>(
      deleteNode({
        target: this.node.target,
        predicates: this.node.predicates,
        allowEmptyPredicates: this.node.allowEmptyPredicates,
        returning: projectionItems,
      }),
    );
  }
}
```

Reuses `toProjectionItem` from `src/query/projection.ts` (lifted
out of `Relation` in v1.7) and `ProjectedShape` from
`src/query/types.ts`.

New file `src/query/DeletableScope.ts`:

```ts
export class DeletableScope<
  TableName extends string,
  Columns extends ColumnsShape,
> extends Relation<Columns> {
  constructor(
    node: RelationNode,
    private readonly target: TableRef,
  ) {
    super(node);
  }

  /** Override Relation.where so chaining stays in the scope. */
  override where(
    predicate: Expression<boolean>,
  ): DeletableScope<TableName, Columns> {
    return new DeletableScope<TableName, Columns>(
      whereNode(this.node, predicate.node),
      this.target,
    );
  }

  /** Build a DELETE statement using the accumulated predicates. */
  delete(): Delete<Columns, null> {
    const predicates = collectWherePredicates(this.node);
    return new Delete<Columns, null>(
      deleteNode({
        target: this.target,
        predicates,
        allowEmptyPredicates: false,
      }),
    );
  }
}

/**
 * Walk a Where-chain rooted at a TableRef and return its
 * predicates in source order. Throws if the chain bottoms out at
 * something other than a TableRef — by construction (only this
 * scope and `Table.where` build these nodes) this is unreachable
 * and indicates a programmer error.
 */
function collectWherePredicates(
  node: RelationNode,
): readonly ExpressionNode[] {
  const predicates: ExpressionNode[] = [];
  let current: RelationNode = node;
  while (current.kind === "Where") {
    predicates.unshift(current.predicate);
    current = current.source;
  }
  if (current.kind !== "TableRef") {
    throw new Error(
      "DeletableScope must wrap a Where-chain rooted at a TableRef.",
    );
  }
  return predicates;
}
```

`src/schema-runtime/defineTable.ts` — extend `Table` type and the
runtime construction. The new `.where` overrides `Relation.where`
on the type level (intersection narrows the return type to
`DeletableScope`, which extends `Relation`, so it's covariant and
compatible).

```ts
export type Table<Alias, Columns> =
  Relation<Columns> &
  Readonly<{ _tableName: Alias; _schema: string }> &
  { readonly [Name in keyof Columns & string]: Column<Alias, Name, Columns[Name]> } &
  {
    as<NewAlias extends string>(alias: NewAlias): Table<NewAlias, Columns>;
    insert(attrs: InsertableAttrs<Columns>): Insert<Columns, null>;
    where(predicate: Expression<boolean>): DeletableScope<Alias, Columns>;
    delete(): Delete<Columns, null>;
    deleteAll(): Delete<Columns, null>;
  };
```

If TS rejects the `.where` override (intersection conflict with
`Relation.where`), fall back to `Omit<Relation<Columns>, "where">`
in the intersection. Verified by tsc during Commit B.

Implementation in `buildTable` adds three methods alongside the
existing `as`/`insert`:

```ts
where(predicate: Expression<boolean>) {
  return new DeletableScope(whereNode(node, predicate.node), node);
},
delete() {
  return new Delete<Columns, null>(
    deleteNode({ target: node, allowEmptyPredicates: false }),
  );
},
deleteAll() {
  return new Delete<Columns, null>(
    deleteNode({ target: node, allowEmptyPredicates: true }),
  );
},
```

Note: the `node` captured here is the `TableRef` built earlier in
`buildTable`. `Table.delete()` produces a `DeleteNode` with empty
predicates and `allowEmptyPredicates: false` — it's a runtime
footgun catch, not a usable API path.

### `Database.run` overloads

`src/executor/Database.ts` — add Delete overloads ahead of the
existing Insert and Relation overloads. Order: Delete-with-Returning,
Delete-without, Insert-with-Returning, Insert-without, Relation.
(Within each class the more-specific Returning overload comes first;
between classes, order doesn't matter because they're discriminated
by the class.)

```ts
run<Columns extends ColumnsShape, Returning extends ColumnsShape>(
  remove: Delete<Columns, Returning>,
  client?: PoolClient,
): Promise<RowOf<Returning>[]>;

run<Columns extends ColumnsShape>(
  remove: Delete<Columns, null>,
  client?: PoolClient,
): Promise<{ readonly rowCount: number }>;
```

Implementation: extend the `instanceof` cascade.

```ts
if (query instanceof Delete) {
  const compiled = deleteToSql(query.node);
  const result = await runner.query(compiled.text, [...compiled.params]);
  if (query.node.returning === null) {
    return { rowCount: result.rowCount ?? 0 };
  }
  return result.rows;
}
```

## Open questions / risks

- **`.where` override on `Table` type.** Adding `.where` to the
  intersection alongside the inherited `Relation.where` should
  resolve to the more specific return type
  (`DeletableScope`-narrowing intersection); if TS surfaces a
  conflict instead, fall back to
  `Omit<Relation<Columns>, "where">`. Verified during Commit B.
- **`collectWherePredicates` walks the source chain.** It
  duplicates a small slice of the `collect` function in
  `serialise.ts`. Acceptable for v1.8; if a third caller appears,
  lift into a shared helper. No behaviour drift today because
  both walkers handle only the `Where`/`TableRef` cases (the
  scope is constrained to those by construction).
- **`Table.delete()` is a footgun catch, not a feature.** It
  exists only so that an accidental empty-WHERE delete throws
  with a clear pointer. Document it as such in the
  README/jsdoc — users should always go through
  `.where(...).delete()` or the explicit `.deleteAll()`.
- **No predicate-tree validation against target columns.** A
  user can today write `users.where(orders.id.eq(1)).delete()`
  and Postgres rejects it at execution. Stricter compile-time
  checks would require a `DeletePredicate` type narrower than
  `Expression<boolean>`; deferred — same posture as v1.7.

## Deferred (still post-v1.8)

- **Rails-style `users.where(...).insert(attrs)` chain.** Sketched
  in the v1.7 plan; v1.9 work. Requires a runtime extractor for
  top-level AND of `column.eq(literal)` predicates plus an
  `InsertableScope` mirroring `DeletableScope`.
- **`UPDATE`.** Its own AST + serialiser + fluent class; same
  shape as Insert/Delete. Adds an attribute-set payload and
  WHERE.
- **`DELETE ... USING`** (multi-table delete) — useful but
  separate; needs join-style relation tracking on the DELETE node.
- **`ON CONFLICT` for INSERT, transactions, streaming.** Already
  deferred from earlier iterations; unchanged.
