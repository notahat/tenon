# `tenon` — FK-inferred joins (v1.10)

## Context

`tenon` already has compile-time-safe `innerJoin(...).on(...)` and
`Table.as(...)` for self-joins (v1.4–v1.6). The duplicate-column
brand pattern in `MergedColumns` is the precedent for surfacing
type-level errors at `db.run(...)` time.

Right now every join requires an explicit `.on(predicate)`. In the
overwhelmingly common case — two tables linked by a single foreign
key — the user is rewriting information that's already in the
database catalog. This iteration teaches `tenon` to read FK
metadata during introspection and use it to make `.on(...)`
optional when the FK between the two sides is unambiguous. Where
the FK is ambiguous or absent, the existing explicit `.on(...)`
flow is unchanged.

User-selected scope decisions (made up-front):

- **Same `innerJoin` method.** No new method, no second
  abstraction. `users.innerJoin(posts)` becomes runnable directly
  when an unambiguous FK connects the two sides; `.on(...)` is
  still available as an override.
- **Threaded FK metadata.** A new generic on `Relation` carries
  the FK records that flow with it, so chained joins
  (`a.innerJoin(b).innerJoin(c)`) and post-`where` joins all
  participate in inference.
- **Self-joins always require `.on(...)`.** When both sides resolve
  to the same physical table, FK direction is ambiguous; the type
  system rejects implicit-ON and forces `.on(...)`.
- **Single-column FKs only in v1.** Composite FKs are recorded by
  the introspector but skipped by the inference path. v1.1 can
  lift this once the basics work.

## Decisions

- **FK metadata lives on the `Table`, not on individual columns.**
  An optional fourth argument to `defineTable` carries an array of
  FK records. Stored as a private `_foreignKeys` field on the
  table, threaded into the type via a new generic.
- **Inference brand pattern matches duplicate-column brand.**
  When no unambiguous FK exists, the merged-relation type carries
  a literal-template error message that surfaces at `db.run(...)`.
  Users see a TypeScript error like
  `tenon: cannot infer join predicate; call .on(...) — no FK
  between users and orders`.
- **`JoinBuilder` extends `Relation` unconditionally.** This is
  the cleanest way to make a `JoinBuilder` runnable without
  `.on(...)`. The "ambiguous → must call `.on()`" check rides on
  the brand in the merged-relation type, not on whether
  `JoinBuilder extends Relation`.
- **Runtime fallback at serialise time.** If `.on(...)` was never
  called by the time the join is serialised, the serialiser looks
  up the FK metadata and constructs the equivalent
  `ExpressionNode` itself. A defensive runtime throw covers the
  "type system was bypassed" case.
- **Tests are written first per commit (TDD per CLAUDE.md).**
  Each commit lands the failing test, then the implementation.
- **No bidirectional symmetry to design.** A foreign key is
  directed (`posts.authorId → users.id`), but the *resulting* ON
  predicate is symmetric (`posts.authorId = users.id`). So
  `users.innerJoin(posts)` and `posts.innerJoin(users)` both fire
  inference and produce the same predicate (with operands ordered
  to match the FK's referencing/referenced sides).
- **Cross-schema FKs are first-class.** The catalog query records
  schema names on both sides; FK records carry full
  `(schema, table, column)` triples.

## Design

### Runtime FK record

```ts
// In src/schema-runtime — same module surface as defineTable.
export interface ForeignKey {
  readonly name: string;                       // constraintName
  readonly columns: readonly string[];         // referencing
  readonly referencedSchema: string;
  readonly referencedTable: string;
  readonly referencedColumns: readonly string[];
}
```

`defineTable` gains an optional fourth argument:

```ts
defineTable<TableName extends string, Columns extends ColumnsShape>(
  schema: string,
  name: TableName,
  columns: Columns,
  foreignKeys?: readonly ForeignKey[],
): Table<TableName, Columns, ForeignKeys>;
```

`Table.as("alias")` preserves `_foreignKeys` unchanged — the FK
records reference *physical* table names, not aliases. The
fluent layer resolves alias → physical at inference time.

### Type-level FK record

Mirrors the runtime record. Generic on `Table` and `Relation`:

```ts
type ForeignKeyTuple = readonly {
  readonly fromSchema: string;
  readonly fromTable: string;
  readonly fromColumn: string;
  readonly toSchema: string;
  readonly toTable: string;
  readonly toColumn: string;
}[];
```

For v1, only single-column FKs make it into the type. Composite
FKs are filtered out by the emitter so the inference type doesn't
have to deal with them.

### Threading through `Relation`

`Relation<Columns, FKs extends ForeignKeyTuple = []>` is the new
shape. Every read operator passes `FKs` through unchanged:

```ts
where(predicate): Relation<Columns, FKs>
order(...): Relation<Columns, FKs>
limit(n): Relation<Columns, FKs>
offset(n): Relation<Columns, FKs>
project(...): Relation<ProjectedShape<...>, FKs>  // FKs preserved
```

`Table<Alias, Columns, FKs>` extends `Relation<Columns, FKs>`.

`MergedColumns<L, R>` becomes `MergedRelation<LCols, LFKs, RCols, RFKs>`
with two outputs:

- merged columns shape (with the existing duplicate-column brand)
- merged FKs union (`[...LFKs, ...RFKs]`)

### Inference type

```ts
type InferJoinPredicate<LFKs, RFKs, LTable, RTable> =
  // Find FKs from L→R or R→L between the two physical tables.
  // Filter to single-column FKs.
  // If exactly one match → return { from, to } pair.
  // If zero or >1 → return error brand.
  // If LTable === RTable physically → return self-join brand.
```

The brand is a literal-template error message that survives
through `.where`/`.order`/`.limit` and is checked by `db.run(...)`.

### `JoinBuilder` change

```ts
class JoinBuilder<LCols, LFKs, RCols, RFKs, LTable, RTable>
  extends Relation<MergedCols, MergedFKs> {

  // Existing override path:
  on(predicate): Relation<MergedCols, MergedFKs>;
}
```

`JoinBuilder` extending `Relation` means calling `db.run(jb)`,
`.where(...)`, etc. all work directly. The merged-relation type
carries the inference brand if FK is ambiguous; that brand
surfaces at `db.run(...)` exactly like duplicate columns do today.

### Runtime: ON predicate construction at serialise time

The AST `InnerJoin` node's `on` field becomes
`ExpressionNode | null`. When null, the serialiser:

1. Resolves the left and right sides to physical tables (walking
   through aliases as needed).
2. Looks up FK records from both tables' `_foreignKeys`.
3. Filters to FKs connecting these two physical tables, single
   column, not self-referential.
4. If exactly one match: builds the equivalent `ColumnRef = ColumnRef`
   `ExpressionNode` and emits.
5. Otherwise throws — defensive, type system should have caught
   it.

### Catalog and emitter

`readCatalog` gains a sibling query for `pg_constraint` filtered to
`contype = 'f'`, joined to `pg_class` and `pg_namespace` for
table/schema names and `pg_attribute` (with `unnest` over `conkey`
and `confkey`) for column names. Returns
`CatalogForeignKey[]` parallel to `CatalogColumn[]`.

`emit.ts` gains a fourth argument to its rendered `defineTable`
call. Composite FKs are dropped at emission time with a generated
comment so the user can see they were detected but skipped.

## Open questions / risks

- **TypeScript editor performance** with FK threading on a real
  schema. Out of scope to measure pre-implementation per user
  decision; revisit if anyone flags slowness.
- **Inference scope on aliases.** The fluent layer resolves
  aliases to physical tables for FK lookup. If a user aliases
  *both* sides of a non-self-join (e.g. `users.as("u")` and
  `posts.as("p")`), inference must still work. The type-level
  detection of "physically the same table" must not trigger here.
- **AST field nullability.** Making `InnerJoin.on` nullable is a
  breaking change to anyone depending on the AST shape directly.
  AST is unstable / pre-1.0; document the change in the plan.
- **Composite FKs surfaced later.** Type-level support for
  composite FKs is non-trivial (paired tuple alignment). Deferred
  to v1.10.1 or v1.11; the catalog already stores them so the
  upgrade is purely additive.

## Deferred (post-v1.10)

- Composite FK inference.
- `leftJoin` / `rightJoin` / `fullJoin` with FK inference (also
  blocked on the outer-join iteration itself).
- Active-record-style accessors (`users.posts`, `posts.author`).
  Possible but a much bigger conceptual jump; reconsider once v1
  inference has shipped.
- Joining sub-queries / CTEs with FK inference. Today the right
  side of `innerJoin` must be a defined table; that constraint is
  unchanged.
- `USING (column)` SQL syntax.
