# tenon — UUID primary key support (v1.15)

## Context

UUIDv7 primary keys already work in tenon. The library has no
type-system or runtime barrier to using a `uuid` column as a PK:

- `src/introspect/mapTypes.ts` maps Postgres `uuid` to TypeScript
  `string`.
- `Table.find(id)` is generic over the PK column's TS type
  (`Columns[Col]["_tsType"]`), so it accepts any `string`.
- `InsertableAttrs` already makes a column optional when
  `hasDefault: true`, so a column declared `id uuid PRIMARY KEY
DEFAULT uuidv7()` is omittable on insert.

What's missing is _visibility_: nothing in the docs tells a user this
pattern is supported, and there's no executable example confirming
the end-to-end shape (DB-side generation + client-side override + PK
lookup) holds together.

The deliverable is therefore documentation plus one integration test
that exercises the supported pattern. No library code changes.

## Decisions

- **No `Uuid` branded type.** Keep `uuid` → `string`, consistent with
  the existing `int8` / `numeric` / `timestamp` → `string` mappings
  and with the `uuid` npm package's own typings. Branding would be
  the odd one out and would force casts at every boundary (HTTP,
  JSON, env vars, third-party libs).
- **PG18 only.** Illustrate the builtin `uuidv7()` server-side
  default. Older-Postgres workarounds (`pg_uuidv7` extension,
  PL/pgSQL functions) are out of scope.
- **No bundled generator.** Users who want client-side generation
  bring the `uuid` npm package (v10+ has `v7()`). Tenon adds no new
  exports.
- **Client override is the existing rule.** A user supplying `id:
v7()` on insert wins over the DB default; this falls out of the
  current insert builder with no changes.

## Design

### New: `docs/guide/uuids.md`

A short page that:

- States UUID primary keys are supported and shows the recommended
  PG18 schema:

  ```sql
  CREATE TABLE users (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    email text NOT NULL
  );
  ```

- Shows the two insert shapes side by side:

  ```ts
  // Server-generated id (PG18 default fires).
  const created = await db.run(
    users.insert({ email: "pete@notahat.com" }).returning(users.id),
  );

  // Client-supplied id (overrides the default).
  import { v7 as uuidv7 } from "uuid";
  await db.run(users.insert({ id: uuidv7(), email: "..." }));
  ```

- Shows `db.run(users.find(id))` round-tripping a UUID PK.
- Notes the column type is plain `string`, with a one-line link to
  `type-mapping.md` explaining the no-brand policy (parity with
  `int8` / `numeric`).
- Cross-links to `inserts.md` for the required/optional/forbidden
  column rules that make this work.

### New: `test/integration/uuid-primary-key.test.ts`

Uses `withTestSchema`. Gated on `server_version_num >= 180000` so it
skips with a clear message on older Postgres.

Cases:

- Create `users (id uuid PRIMARY KEY DEFAULT uuidv7(), email text
NOT NULL)`.
- `db.run(users.insert({ email }).returning(users.id))` returns a
  row whose `id` is a syntactically-valid UUID with version nibble
  `7`.
- `db.run(users.insert({ id: clientValue, email }))` honours the
  client value — confirmed by `db.run(users.find(clientValue))`
  returning the same row.
- `db.run(users.find(missingId))` rejects with `RowNotFoundError`
  (sanity check that v1.14's throwing contract still holds for UUID
  PKs).

The test imports `v7` from `uuid` (already a `devDependency` if
present; if not, add it as one). Generation parity with PG's builtin
isn't asserted — we only need a v7 UUID, and `uuid` produces them.
