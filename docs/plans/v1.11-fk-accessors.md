# `tenon` — FK accessors via `find` (v1.11)

## Context

`tenon` already auto-discovers foreign keys for `innerJoin` ON-clause
inference (v1.10). This iteration takes the FK metadata further: from
a single-row "anchor" obtained by primary-key lookup, walk
associations the way ActiveRecord does. Two motivating examples:

```ts
posts.find(1).comments; // Relation<commentsColumns>: all comments on post 1
comments.find(5).post; // SingleRow<postsColumns>: the parent post of comment 5
```

Three things are new in `tenon`'s model:

1. A **primary-key concept** (until now only foreign keys were
   captured).
2. A **single-row** value type alongside `Relation` (everything has
   resolved to an array of rows so far).
3. **Schema-level wiring** so a `Table` type can refer to other
   `Table` types in its accessor results (FK metadata currently
   carries only strings).

The win is that all paths rooted at `find` need only single-roundtrip
joins — no sub-queries, no `DISTINCT`, no duplication corner cases.
An earlier "filtered child relation" framing
(`posts.where(...).comments`) was considered and explicitly dropped
in discussion; this design ducks its messy semantic edges entirely.

## Decisions

- **`find` is the only entry point for accessor walks.** Accessors
  live on `SingleRow` only; plain `Relation` chains do not get them.
  The path to add them later is purely additive.
- **Single-column primary keys only.** `Table.find` is omitted from
  tables with composite or absent PKs, surfacing as a "property does
  not exist" error at the call site. Composite PKs are recorded
  faithfully but don't get a `find` method.
- **Both directions get accessors.** Belongs-to (FK out) and
  has-many (FK in).
- **Naming derived literally.** Belongs-to from the FK column,
  stripping a trailing `_id` (`author_id` → `author`); fall back to
  the referenced table name verbatim if no `_id` suffix. Has-many
  uses the referencing table's physical name verbatim (`comments`).
  No singularisation library.
- **Not-found returns `null`** from `db.run(singleRow)`. A separate
  `singleRow.orThrow()` produces a `SingleRowOrThrow<C>` whose
  `db.run` throws `RowNotFoundError` instead.
- **No new AST nodes.** Accessor results compile to existing
  `Where`, `InnerJoin`, `Project`, `Limit` shapes. No sub-queries,
  no `DISTINCT`.
- **Wiring via `defineSchema`.** A new public function in
  `schema-runtime` takes a record of tables and returns a wired bag
  where each table's `find` produces SingleRows with accessor
  methods merged in. Type-level lookup keys by
  `${schema}.${physicalName}` rather than the user-chosen object
  key, so hand-rolled schemas with renamed exports still work.

## Approach

### `SingleRow<Columns>`

A new fluent-layer class that wraps a `RelationNode`, just like
`Relation`, but signals at the type level "produces 0 or 1 rows".
Lazy, composable, executes via `db.run`.

- `db.run(singleRow)` returns `Promise<RowOf<Columns> | null>`.
- `singleRow.orThrow()` returns a `SingleRowOrThrow<Columns>` whose
  `db.run` returns `Promise<RowOf<Columns>>` and throws on
  no-row-found.
- Accessor methods (added by `defineSchema`) follow association
  edges.

Belongs-to from a single row stays single-row; has-many fans out:

- `SingleRow<post>.author` → `SingleRow<users>`
- `SingleRow<post>.comments` → `Relation<comments>`

### `Table.find(id)`

Available only on tables with a single-column primary key. The id
parameter type is `Columns[PkColumn]["_tsType"]`, so
`posts.find("hello")` fails to compile when `id` is `int4`.

```ts
posts.find(1);
// AST equivalent: posts.where(posts.id.eq(1)).limit(1)
// Type: SingleRow<postsColumns> + accessor methods (after defineSchema)
```

### Accessor SQL emission

`posts.find(1).comments`:

```sql
SELECT comments.*
FROM comments
INNER JOIN posts ON comments.post_id = posts.id
WHERE posts.id = $1
```

`comments.find(5).post`:

```sql
SELECT posts.*
FROM posts
INNER JOIN comments ON posts.id = comments.post_id
WHERE comments.id = $1
LIMIT 1
```

### `defineSchema({ users, posts, comments })`

Two responsibilities:

- **Runtime**: builds a `Map<schema.physicalName, Table>`, then
  `Object.assign`s accessor methods onto each `find`-produced
  `SingleRow` instance. No mutation of the input Tables themselves
  — the lookup map is captured by closure on each table's `find`.
- **Type-level**: returns
  `{ [K in keyof S]: WiredTable<S[K], S> }`, where `WiredTable`
  adds the typed `find` method, and `find`'s return type is
  `SingleRow<...>` intersected with the type-level association map.

Generated schemas import `defineSchema` and emit
`export const schema = defineSchema({ users, posts, comments })`
after the per-table exports. Hand-written schemas use it the same
way.

### Type-level association map

```ts
type AccessorsFor<T, S> = BelongsToAccessors<T, S> & HasManyAccessors<T, S>;
```

`BelongsToAccessors` walks `T["_foreignKeys"]`, looks up each
single-column FK's referenced table in `S`, and produces an
accessor-keyed record. `HasManyAccessors` walks every other table
in `S`, finds incoming FKs to `T`, and produces accessors. Both
emit branded types when ambiguous (the existing
`MissingFkBrand` / `AmbiguousFkBrand` machinery is the precedent).

## Sequencing

Each step ends with tests passing and a commit.

### Step 1 — Primary key metadata

- Add `src/schema-runtime/primaryKey.ts` with the metadata type.
- Extend `defineTable` to accept and carry primary keys.
- Update `Table` type to expose `_primaryKey` (phantom + runtime).
- `tenon-generate`: read PKs from `pg_catalog`, emit them in the
  generated schema.
- Tests: type tests that PK threads through `Table.as`, runtime
  test that `_primaryKey` is preserved, generator unit test.
- No behavior change yet; this is plumbing.

### Step 2 — `SingleRow` and `Table.find` (no associations yet)

- Add `src/query/SingleRow.ts` (with `SingleRowOrThrow` and
  `RowNotFoundError` alongside).
- Add `find` method on `Table` (only when PK is single-column at
  the type level).
- `Database.run` gains overloads for `SingleRow` and
  `SingleRowOrThrow`. Returns `RowOf<C> | null` and `RowOf<C>`
  respectively.
- Tests: type tests for `find` argument typing, `find` absent on
  composite-PK tables, runtime tests for both null-found and
  orThrow paths against real SQL emission.

### Step 3 — `defineSchema` + has-many accessors

- Add `src/schema-runtime/defineSchema.ts`. Runtime: builds the
  lookup map, computes accessor methods to attach to SingleRows.
  Type-level: returns wired-table types.
- Add `src/query/accessor-naming.ts` with the derivation rules
  (used by both runtime wiring and the type-level transform via
  parallel template-literal types).
- Implement has-many accessors only in this step.
- Add `AmbiguousHasManyBrand` to `src/query/types.ts`; extend the
  `UnbrandedColumns` constraint set.
- Tests: `posts.find(1).comments` runs and emits correct SQL;
  ambiguous case (`users.messages`) brands at `db.run` time;
  column-name collision skips silently with a generated comment.

### Step 4 — Belongs-to accessors

- Extend `defineSchema` to also wire belongs-to accessors. Result
  type: plain `SingleRow<Ref>`. **Chained walks (`.post.author`)
  are scoped out for v1**: the type-level result is a plain
  `SingleRow`, not a `WiredSingleRow`, so a follow-up `.author`
  doesn't compile. Implementing chained walks needs a chained-join
  runtime (each accessor extends an existing join chain rather
  than starting a new query) — left to a v1.12 follow-up; the
  surface stays additive.
- Tests: `comments.find(5).post` runs and emits correct SQL;
  the SQL is `SELECT parent.* FROM parent JOIN child ON ... WHERE
child.pk = $1 LIMIT 1`; nullable FK still types as
  `SingleRow<users>` whose `db.run` may return null (no
  special-casing).

### Step 5 — Documentation and integration test

- New `docs/guide/relationships.md` with worked examples.
- `docs/architecture/fluent-layer.md`: SingleRow's place;
  defineSchema's role.
- `docs/architecture/types-and-phantoms.md`: the new
  association-map type machinery.
- `docs/reference/single-row.md`, `docs/reference/define-schema.md`.
- README example showing `find` and one accessor.
- Integration test against a fixture schema covering: single FK,
  multi-FK ambiguity, cross-schema FKs, nullable belongs-to,
  has-many fan-out, `find().orThrow()` not-found case, recursive
  walk.

## Out of scope for this iteration

- **Composite primary keys**: the `find` method is omitted; users
  with composite PKs use `where(...).limit(1)` and don't get
  associations.
- **Composite foreign keys**: already filtered at emit time today;
  no change.
- **`findBy({ ... })`** for non-PK lookups.
- **Chained `find` on a `Relation`** (`posts.find(1).comments.find(5)`):
  out of scope; `comments.find(5)` covers the same use case.
- **Chained association walks** (`comments.find(5).post.author`):
  belongs-to and has-many accessors return non-recursive values
  in v1. Implementing the chained-join runtime needed to make
  walks compose is the natural v1.12 follow-up; the surface stays
  the same when it lands.
- **Accessors on plain `Relation` chains** (`posts.where(...).comments`):
  explicitly dropped per discussion.
- **`update` / `delete` directly on `SingleRow`**: natural
  extension but out of scope for v1; users go via the existing
  `where(...).delete()` chain.
- **Pluralisation / singularisation libraries**: accessor names
  are derived literally; users with very irregular naming can
  rename via a future override hook.
- **Polymorphic / through-associations**: not modelled.

## Open questions to validate during implementation

- **Recursive accessor depth**: TypeScript will refuse arbitrarily
  deep recursion on accessor types (`SingleRow<a>.b.c.d.e...`). A
  depth bound around 4-5 should be plenty; if it bites, we cap
  depth and document. Users wanting deeper walks fall back to
  explicit joins.
- **`find` parameter naming when the PK column has an unusual
  name**: the `find` signature uses the literal PK column name,
  so a PK named `uuid` or `slug` works without special casing.
- **Self-referential FKs** (e.g. `users.manager_id → users.id`):
  belongs-to accessor `manager` works trivially. Has-many on the
  `users` side could be `users` again (collides with own table
  name) — likely skip with a comment, same as the column-collision
  rule.
