# `trel` — table aliasing + free-composition joins (v1.6)

## Context

`trel` v1.5 shipped INNER JOIN with a strict design: `OnPredicate<L, R>`
brands the `.on()` argument when the two sides share any column name, so
the user gets a compile error at the join site. In practice that's too
tight — `users.innerJoin(teams).on(users.team_id.eq(teams.id))` is the
canonical join and is currently rejected because both tables have `id`.
The brand also blocks self-joins entirely, since aliasing the same table
yields identical column shapes.

This iteration moves the duplicate-column check from `.on()` to `db.run`,
and adds `.as("alias")` so users can rename a table for self-joins (and
for cosmetic disambiguation when projecting). After this iteration:

- Joins between tables that share column names compose freely; `.where`,
  `.order`, and `.project` all work on the merged shape.
- The only thing that fails to compile is `db.run(joined)` when the row
  shape would have duplicate keys (and you didn't `.project(...)`). The
  error names the offending columns.
- `users.as("u")` returns a fresh `Table` whose internal alias is `"u"`;
  column accessors qualify as `"u"."id"`. Self-joins work end-to-end.

## Decisions

- **Brand moves from `OnPredicate` to `MergedColumns`.** The collision
  signal lives on the columns shape itself, so it bubbles through
  `.where` / `.order` and only fires at `db.run`. `.project(...)` clears
  it because `ProjectedShape<Items>` is a fresh object type with no
  brand.
- **`.as(alias)` lives on `Table`, not on `Relation`.** Aliasing a derived
  relation needs subqueries, which are still deferred. Only
  `defineTable(...)` results expose `.as`.
- **Aliased tables are still valid right-hand sides for `.innerJoin`.**
  The `_tableName` / `_schema` constraint is preserved on the result of
  `.as`, so `users.innerJoin(users.as("u2")).on(...)` typechecks.
- **`_tableName` becomes "alias", not "physical name".** Today the
  phantom equals the physical name because no aliasing exists. After
  `.as("u")`, the phantom is `"u"`. Existing code is unaffected (it
  uses `_tableName` only as a string identity for the `innerJoin`
  constraint). Comments are updated to reflect the new meaning.
- **No changes to outer joins, sub-query joins, or aggregates.** Still
  deferred.

## Design

### `MergedColumns` carries the collision tag

`src/query/types.ts`:

```ts
export type DuplicateColumnNames<L, R> = Extract<keyof L & keyof R, string>;

export type MergedColumns<
  L extends ColumnsShape,
  R extends ColumnsShape,
> = DuplicateColumnNames<L, R> extends never
  ? Readonly<L & R>
  : Readonly<L & R> & {
      readonly __trelDuplicateColumns: `trel: joined relation has duplicate columns: ${DuplicateColumnNames<L, R>}; .project(...) before db.run, or .as(...) one side before joining`;
    };
```

Removed: `OnPredicate<L, R>`. The brand and message it carried move to
`MergedColumns` in the same shape, keyed on `__trelDuplicateColumns`.

`src/query/JoinBuilder.ts`:

```ts
on(predicate: Expression<boolean>): Relation<MergedColumns<Left, Right>>;
```

`.on()` is back to taking a plain `Expression<boolean>`.

### `Database.run` rejects branded shapes

`src/executor/Database.ts`:

```ts
async run<Columns extends ColumnsShape>(
  query: Relation<Columns> & {
    readonly _columns: { readonly __trelDuplicateColumns?: never };
  },
  client?: PoolClient,
): Promise<RowOf<Columns>[]>;
```

When `Columns` has the `__trelDuplicateColumns` tag, the constraint
fails and the user sees the message embedded in the tag. `.project(...)`
returns `Relation<ProjectedShape<Items>>`, which has no tag, so chaining
projection clears the error.

(`Relation`'s phantom `_columns: Columns` is what we read against —
already declared in `src/query/Relation.ts`.)

### `Table.as(alias)`

`src/schema-runtime/defineTable.ts`:

```ts
export type Table<
  TableName extends string,
  Columns extends ColumnsShape,
> = Relation<Columns> &
  Readonly<{
    _tableName: TableName;  // now means "alias used in column refs"
    _schema: string;
  }> & {
    readonly [Name in keyof Columns & string]: Column<
      TableName,
      Name,
      Columns[Name]
    >;
  } & {
    as<NewAlias extends string>(alias: NewAlias): Table<NewAlias, Columns>;
  };
```

Implementation: `as(newAlias)` constructs a fresh `Table` by:
1. Pulling `schema` and physical `name` off the existing TableRef node.
2. Building a new `Relation` whose node is
   `tableRef({ schema, name, alias: newAlias })`.
3. Building Column accessors with `tableAlias = newAlias`.
4. Setting `_tableName = newAlias`, `_schema = schema`.
5. Re-exposing `.as`, so `.as("u").as("v")` works (cheap; no real
   reason to forbid).

Refactor: extract a private `buildTable(schema, name, alias, columns)`
helper out of the existing `defineTable` body so `defineTable` and
`as` share construction logic. `defineTable` calls
`buildTable(schema, name, name, columns)`. `as` calls
`buildTable(schema, name, newAlias, columns)`.

### Critical files

- `src/query/types.ts` — replace `OnPredicate<L, R>` with the
  `MergedColumns` brand. Remove the `OnPredicate` type and its export.
- `src/query/JoinBuilder.ts` — change `.on(predicate)` parameter to
  plain `Expression<boolean>`. Drop the `OnPredicate` import.
- `src/executor/Database.ts` — add the `__trelDuplicateColumns?: never`
  constraint on `run`'s `query` parameter.
- `src/schema-runtime/defineTable.ts` — extract `buildTable` helper, add
  `as` method on the returned object, add `as` to the `Table` type.
- `src/index.ts` — keep `MergedColumns` as a public type export. (No
  `OnPredicate` was exported, so nothing to remove there.)

## Incremental commits

### Commit A — move the brand from `OnPredicate` to `MergedColumns` + run-time gate

- Update `src/query/types.ts`: delete `OnPredicate`, brand
  `MergedColumns`.
- Update `src/query/JoinBuilder.ts`: simplify `.on` signature.
- Update `src/executor/Database.ts`: add the
  `__trelDuplicateColumns?: never` constraint.
- Update `test/unit/join-types.test-d.ts` per above.
- All existing unit/serialise/integration tests stay green; one type
  test changes (the collision moves from `.on()` to `db.run`).

This commit is reviewable on its own — it's a pure type-system move
plus a behavioural improvement (joins between tables sharing a column
name now compose freely, instead of failing at the join site). Self-
joins are still impossible until commit B because there's no way to
construct two relations with distinct aliases over the same physical
table.

### Commit B — `.as("alias")`

- Refactor `defineTable` to share construction with `as`.
- Add `as` method + type.
- New unit + integration tests.

After commit B, the user's example self-join compiles and runs.

2. `tsc --noEmit` clean; `eslint .` clean; `prettier --check .` clean.
3. Smoke checks (must compile and emit the expected SQL):

   // commit A:

     users

       .project(users.email, teams.name),

4. Type-error spot checks (must fail to compile, with the duplicate-

   - `db.run(users.innerJoin(teams).on(users.team_id.eq(teams.id)))`

   - `db.run(users.innerJoin(users.as("u2")).on(...))` without
     `.project(...)` — duplicate everything.

## Open questions / risks

- **Tooltip readability of the brand error.** `__trelDuplicateColumns`
  in tooltips is reasonable but not perfect. Validate during
  implementation; if poor, switch the brand key to a longer descriptive
  literal and let the user read it from the error.
- **`.as` on a derived relation is intentionally absent.** A user might
  expect `users.where(...).as("u")`. The right answer is "use
  subqueries" which we don't support yet. Document the surface as
  `Table.as`, not `Relation.as`, and rely on the type system to make
  it obvious.
- **Phantom `_tableName` semantics shift.** Existing callers treat it
  as a literal string identity for the `innerJoin` constraint; they
  don't care whether the literal is "physical name" or "alias". Low
  risk; mostly a doc-comment update in `Column.ts`, `defineTable.ts`,
  and `Relation.innerJoin`.

## Deferred (still post-v1)

- LEFT / RIGHT / FULL OUTER joins (next iteration; nullability widening
  is the new type-level concept).
- Joining sub-queries (drop the `_tableName` / `_schema` constraint on
  `innerJoin`'s argument).
- `USING (col)` shorthand.
- Aggregates + `group by` + `having`, set ops, CTEs, DML, transactions,
  streaming.
