# `tenon` — documentation (v1.9-docs)

## Context

`tenon` has shipped seven incremental iterations on `main` (v1
through v1.8 — read operators, joins, aliasing, basic INSERT, basic
DELETE). The README has grown into a one-page tour, but everything
beyond it lives in code comments or in the plan files under
`docs/plans/`. There is no narrative guide, no symbol-level
reference, and no description of how the AST → fluent → serialiser
→ executor pipeline fits together.

The library is still pre-alpha, but the public surface is stable
enough to write down for strangers reading the README cold. The
goal of this iteration is **complete documentation aimed at public
library consumers**, broken into multiple incremental commits so
each commit is reviewable on its own.

User-selected scope decisions (made up-front):

- **All three doc kinds**: API reference, narrative guides, and
  contributor/architecture docs.
- **In-repo markdown** under `docs/`. No static-site generator, no
  TypeDoc — handwritten files that GitHub renders.
- **Three top-level folders**: `docs/guide/`, `docs/reference/`,
  `docs/architecture/`. Mirrors the three doc kinds.
- **Audience**: public library consumers. Treat this as the launch
  reference — written for someone who has never seen tenon.
- **README is trimmed** to an overview that links into the three
  folders. Long-form content moves into `docs/`.
- **Iteration covers complete documentation**, landing across many
  commits.

## Decisions

- **No new tooling.** Plain CommonMark `.md` files. Cross-links use
  relative paths so they resolve both on GitHub and on local
  checkouts.
- **One topic per file.** Each page opens with a one-sentence
  framing line ("what this is, who it's for") so a reader skimming
  the index can see in one glance whether they're in the right
  place.
- **Code samples are copy-paste runnable** and use the existing
  README convention of trailing `^?` comments to show inferred
  types (e.g.
  `//    ^? Array<{ id: number; email: string }>`). This is what
  consumers will reach for first.
- **Reference pages mirror the public exports**, not the file
  layout. One page per logically distinct symbol/area, not one page
  per `src/query/*.ts` file. So `Column`, `AliasedColumn`, and
  `Expression` share a page; `Insert` is its own page.
- **Architecture pages are written from the perspective of someone
  adding a new operator.** That framing keeps them concrete and
  forces them to cover the parts of the codebase that actually
  matter, not the parts that just happen to exist.
- **Wrap markdown at 80 columns** to match the existing README
  style.
- **Filenames are kebab-case** to match `docs/plans/` (existing
  convention).
- **`docs/plans/` is untouched** by this iteration — it is the
  iteration history, not consumer documentation.
- **No emojis.** Matches existing tenon docs style.
- **Reference pages don't try to replace TSDoc.** They cover
  surface, intent, and examples; for exact type signatures and
  per-parameter notes, point readers at the source. (TypeDoc-style
  auto-extraction can come later if it pulls its weight.)

### Page outlines

#### Guide

- **getting-started.md** — install, point `tenon-generate` at a
  database, write your first `SELECT`, run it through `Database`.
  Shortest possible end-to-end example.
- **schema-and-introspection.md** — what `tenon-generate` does,
  what the generated file looks like, when to regenerate, the
  `nullable`/`hasDefault`/`isGenerated` flags and what each
  controls. Cross-link to `tenon-generate` reference.
- **queries.md** — `Relation` and the read operators: `project`,
  `where`, `order`, `limit`, `offset`. The "relations are values,
  operators are transforms" mental model.
- **expressions.md** — `Column`, `AliasedColumn`, expression
  operators (`.eq`, `.isNull`, `.isNotNull`, ordering helpers
  `.asc`/`.desc`), `.as("alias")` for projection.
- **joins.md** — `innerJoin(...).on(...)`, `Table.as(...)` for
  self-joins and disambiguation, the duplicate-column compile-time
  error and how to fix it. Use the `users`/`posts` example from
  the README.
- **inserts.md** — `Table.insert(attrs)`, what the attrs type
  requires/allows/forbids, `.returning(...)`, `{ rowCount }` vs
  rows.
- **deletes.md** — `Table.where(...).delete()`, chained
  predicates, `.returning(...)`, the empty-WHERE guard,
  `Table.deleteAll()` as the explicit escape hatch.
- **running-queries.md** — constructing `Database` from a `pg`
  pool, what `.run()` returns for each query class, optional
  `PoolClient` argument, error propagation.
- **type-mapping.md** — `int8` / `numeric` → `string`,
  `timestamp` (no tz) → `string`, `timestamptz` → `Date`, custom
  types fall back to `string`. Spell out the reasoning so readers
  know why.

#### Reference

One page per public symbol cluster. Each page: short framing line,
exported names with one-line descriptions, signatures with the
shapes consumers care about, and a minimal example.

- **database.md** — `Database`, `.run` overload list, `PoolClient`
  passthrough.
- **relation.md** — `Relation<Columns>` and every operator.
- **table.md** — `Table<Alias, Columns>` (the merged
  Relation+columns shape), `.as`, `.insert`, `.where`, `.delete`,
  `.deleteAll`.
- **column-and-expressions.md** — `Column`, `AliasedColumn`,
  `Expression`, all the comparison/predicate helpers in one place.
- **ordering.md** — `Ordering`, `.asc`/`.desc`.
- **join-builder.md** — `JoinBuilder`, `.on(...)`.
- **insert.md** — `Insert`, `.returning(...)`.
- **delete.md** — `Delete`, `DeletableScope`, `.returning(...)`,
  the empty-WHERE guard.
- **scope.md** — `scope(...)` factory and the `Scope` type.
- **types.md** — `RowOf`, `ProjectableItem`, `ProjectedShape`,
  `MergedColumns`, `InsertableAttrs`, `ComparableTo`. What each
  is for and where it shows up in the public surface.
- **schema-runtime.md** — the `@notahat/tenon/schema-runtime`
  subpath: `columnType`, `defineTable`, `ColumnType`,
  `ColumnsShape`, `Table`. Frame it as "what the generated file
  imports."
- **tenon-generate.md** — CLI flags, env vars, output file
  structure, regen workflow.

#### Architecture

- **overview.md** — the pipeline diagram (AST → fluent →
  serialiser → executor), functional core / imperative shell as
  the organising principle, where types live versus where logic
  lives.
- **ast.md** — `RelationNode`, `ExpressionNode`, `InsertNode`,
  `DeleteNode`. Why Insert and Delete are siblings of
  `RelationNode`, not variants.
- **fluent-layer.md** — `Relation`, `Insert`, `Delete`,
  `DeletableScope`. Phantom fields (`_columns`, `_returning`,
  `_kind`, `_tableName`) and what they buy.
- **serialiser.md** — `relationToSql`, `insertToSql`,
  `deleteToSql`. `EmitContext`, parameter numbering rules,
  predicate AND-ing, the empty-WHERE throw on DELETE.
- **executor.md** — `Database.run` overload dispatch, the
  `instanceof` cascade, why overloads live in the class.
- **types-and-phantoms.md** — `ColumnsShape`,
  `ColumnType<JsType, SqlType, Nullable, HasDefault, IsGenerated>`,
  `RowOf`, `MergedColumns`, the duplicate-column brand,
  `ProjectedShape`. End with a worked example showing a column
  type round-tripping through the pipeline.
- **introspector.md** — `readCatalog` → `mapTypes` → `emit`. What
  the CLI does at runtime; how to extend the type map.
- **adding-an-operator.md** — concrete walkthrough using DELETE
  (v1.8) as the worked example: AST node, factory, fluent class,
  serialiser branch, `Database.run` overload, exports, tests.

### Style

- Wrap prose at 80 columns; longer code lines are fine if the
  alternative reads worse.
- Each page begins with a single sentence describing its scope and
  intended reader.
- Code samples use the existing `^?` inferred-type comment style
  from the README.
- Cross-links use relative paths
  (e.g. `[joins](../guide/joins.md)`).
- No emojis.

## Verification

1. **Markdown rendering**: open `docs/README.md` on GitHub (or via
   a local markdown previewer such as `gh markdown-preview` or VS
   Code's preview) and walk every link, on every page, after every
   commit that adds pages. No broken relative links.
2. **Code samples compile.** For samples that mirror existing test
   code, paste them into a scratch `.ts` file in the project and
   run `tsc --noEmit` against it; for samples that exercise
   runtime behaviour, paste them into an integration test file
   gated by `.skip` and confirm the surrounding file still
   typechecks.
3. **Public-surface coverage check** at commit 10: grep
   `src/index.ts` and `src/schema-runtime/index.ts` for every
   `export` and confirm each name appears in at least one
   reference page.
4. **`prettier --check .`** stays clean across the docs commits
   (Prettier formats Markdown).
5. **No source code or tests change** in any docs commit. `git
diff --stat` for each commit should only touch `docs/**`,
   `README.md`, and `docs/plans/v1.9-documentation.md` (commit 1
   only).

## Open questions / risks

- **Sample drift.** Code samples in docs go stale when the API
  changes. Mitigations available later (executable doctests,
  shared snippet files imported into both docs and tests) are out
  of scope for this iteration; flag any sample that's likely to
  rot so a future iteration can lift it into a test file.
- **Reference vs. TSDoc duplication.** The current plan keeps
  reference pages handwritten. If the surface grows enough that
  hand-maintenance becomes a chore, switch to TypeDoc and treat
  the existing pages as overrides. Not a v1.9 problem.
- **`tenon-generate` CLI surface is small but undocumented in
  detail.** Commit 2 forces a precise description; if I find an
  undocumented flag or env var while writing it, surface that as
  a follow-up rather than fixing it in this iteration.
- **Phantom-type explanations.** The architecture page on phantoms
  is the most likely page to drift into hand-waving. Anchor it in
  a concrete example (a single column flowing from
  `tenon-generate` output to a `db.run` row type).

## Deferred (post-v1.9)

- TypeDoc-driven reference auto-extraction.
- Doctests / verified samples.
- A static documentation site (Docusaurus / Astro Starlight /
  VitePress). Decide once content stabilises.
- Versioned docs. Not needed pre-1.0.
- Tutorials beyond getting-started (e.g. "migrating from Knex",
  "modelling a multi-tenant app"). Out of scope until there's
  demand.
