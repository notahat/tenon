# `tenon` — `find(id).delete()` on SingleRow (v1.12)

## Context

`Table.find(id)` (v1.11) introduced primary-key lookups returning a
`SingleRow<Columns>`. Today, deleting a row by primary key still goes
through the `where`-based path:

```ts
await db.run(posts.where(posts.id.eq(1)).delete());
```

The natural shorthand falls out of `find`:

```ts
await db.run(posts.find(1).delete());
```

This iteration adds that. `Update` is **not** in scope — it doesn't
exist anywhere in `tenon` today (no AST node, no `update()` on
`DeletableScope`, no serialiser), so it's a separate, much larger
feature.

## Decisions

- `.delete()` is exposed on the `find(id)` result only, not on
  `SingleRowOrThrow` or on association-derived SingleRows
  (`comments.find(5).post`).
- `db.run(posts.find(id).delete())` resolves to
  `{ rowCount: 0 | 1 }` — the same contract as the existing
  `Delete<C, null>` path. Caller checks `rowCount` if they care
  about not-found.
- `find(id).delete().returning(...)` falls out of the existing
  `Delete.returning` for free.
- The wrapped `LIMIT 1` is dropped at DELETE time. Postgres has no
  `DELETE ... LIMIT`, and the primary-key predicate already
  restricts the statement to ≤1 row.

## Approach

### Mirror `DeletableScope` with a `DeletableSingleRow` subclass

`Table.where(...)` returns `DeletableScope extends Relation`, which
adds `.delete()` and overrides `.where()` to keep the scope alive.
The natural mirror:

```ts
class DeletableSingleRow<Columns> extends SingleRow<Columns> {
  constructor(
    node: RelationNode,
    private readonly target: TableRef,
    private readonly predicates: readonly ExpressionNode[],
  ) {
    super(node);
  }

  delete(): Delete<Columns, null> {
    return new Delete<Columns, null>(
      deleteNode({
        target: this.target,
        predicates: this.predicates,
        allowEmptyPredicates: false,
      }),
    );
  }
}
```

A subclass instead of methods on plain `SingleRow` because:

- Association-built SingleRows (`comments.find(5).post`) wrap an
  inner-join relation, not a flat `WHERE pk = ?`. Deleting through
  them would need `DELETE USING` or a CTE — out of scope. The type
  system enforces the constraint by giving them plain `SingleRow`,
  not `DeletableSingleRow`.
- Symmetric with the `DeletableScope` / `Relation` split.
- Inherits `_kind: "SingleRow"` so `Database.run`'s `SingleRow`
  overload still matches it. No new dispatch branch on the SELECT
  side.

`DeletableSingleRow` carries `target` and `predicates` explicitly so
`.delete()` doesn't need to walk the wrapped node — the wrapped node
has shape `Limit(Where(TableRef, predicate), 1)`, which the existing
`collectWherePredicates` (used by `DeletableScope`) doesn't handle.

### `Table.find` returns `DeletableSingleRow`

In `src/schema-runtime/defineTable.ts`, the `find` runtime constructs
a `DeletableSingleRow` and threads through the target node and the
single PK predicate:

```ts
find(id: unknown): DeletableSingleRow<Columns> {
  const predicate = binaryOp("=", accessors[pkColumn]!.node, parameter(id));
  return new DeletableSingleRow<Columns>(
    limitNode(whereNode(node, predicate), 1),
    node,           // TableRef — same one Table.where passes
    [predicate],
  );
}
```

`FindMethod<Columns, PK>` in the same file returns
`DeletableSingleRow<Columns>` instead of `SingleRow<Columns>`.

`WiredSingleRow` in `src/query/types.ts` is updated to
`DeletableSingleRow<C> & AccessorsFor<...>` so `find` exposes both
`.delete()` and the wired accessors. Belongs-to accessor values
remain plain `SingleRow` — non-deletable by construction.

### Database dispatch unchanged

`db.run(deletableSingleRow)` matches the existing `SingleRow<C>`
overload (subclass relation, runtime `instanceof SingleRow` is
true). `db.run(posts.find(1).delete())` matches the existing
`Delete<C, null>` overload. No new overloads, no new instanceof
branches.

## Tests

- `test/unit/find.test.ts` — `find().delete()` returns a `Delete`,
  emits `DELETE FROM ... WHERE pk = $1` with no `LIMIT`, preserves
  table aliases, and chains `.returning(...)`.
- `test/unit/find-types.test-d.ts` — `find` returns
  `DeletableSingleRow`; `find().delete()` resolves to
  `Delete<C, null>`; `db.run(...)` types as
  `Promise<{ rowCount: number }>`; `orThrow().delete` is absent.
- `test/unit/belongs-to-types.test-d.ts` — belongs-to accessor's
  `SingleRow` does not expose `.delete()`.
- `test/integration/relationships.test.ts` — exercises
  `find(id).delete()` against `tenon_test`, asserting `rowCount: 1`
  on hit, `rowCount: 0` on miss.

## Out of scope

- `update()` anywhere — neither on `Relation`, `DeletableScope`, nor
  `SingleRow`. Update is a future feature.
- `.delete()` on `SingleRowOrThrow` — read-side decorator; mixing
  throw-on-not-found with delete creates a four-way matrix nobody
  asked for.
- `.delete()` on association SingleRows
  (`comments.find(5).post.delete()`).
- `.delete()` on the `Relation` returned by has-many accessors
  (`posts.find(1).comments.delete()`) — would need has-many
  accessor results to be `DeletableScope`-shaped, which is a
  separate question.
