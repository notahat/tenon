# Schema and introspection

How tenon learns about your database, what gets emitted, and when
to regenerate.

## Why introspect

tenon's compile-time guarantees come from accurate column metadata:
which columns exist on each table, their Postgres types, whether
they're nullable, whether they have defaults, whether they're
generated. There is no schema DSL — that information already lives
in the database catalog, and `tenon-generate` reads it directly.

The output is a plain TypeScript module that imports from
`@notahat/tenon/schema-runtime`. Everything else in tenon —
queries, inserts, deletes, joins — is built on top of the
`Table` values that module exports.

## The CLI

```sh
npx tenon-generate \
  --database-url postgres://localhost/myapp_dev \
  --schemas public \
  --output src/schema.ts
```

Three flags:

- `--database-url` (required) — any Postgres connection string `pg`
  understands.
- `--schemas` (optional, defaults to `public`) — comma-separated
  list of schemas to introspect.
- `--output` (required) — the file to write. Overwritten on every
  run.

See the [`tenon-generate` reference](../reference/tenon-generate.md)
for the full surface.

## What gets emitted

For each table the CLI produces a `defineTable(...)` call with one
column per row in `information_schema.columns`. Roughly:

```ts
// This file is generated by tenon-generate. Do not edit by hand.
// Re-run `tenon-generate` after schema migrations.

import { columnType, defineTable } from "@notahat/tenon/schema-runtime";

export const users = defineTable("public", "users", {
  id: columnType<number, "int4">({
    nullable: false,
    hasDefault: true,
    isGenerated: false,
  }),
  email: columnType<string, "text">({
    nullable: false,
    hasDefault: false,
    isGenerated: false,
  }),
  createdAt: columnType<Date, "timestamptz">({
    nullable: false,
    hasDefault: true,
    isGenerated: false,
  }),
});
```

Each column carries five pieces of information:

- The **TypeScript type** the column reads back as (the first type
  parameter — `number`, `string`, `Date`, ...).
- The **Postgres type tag** (the second type parameter — `"int4"`,
  `"text"`, `"timestamptz"`, ...). Used by tenon to enforce
  cross-column type compatibility in expressions.
- `nullable` — `true` if the column accepts NULL.
- `hasDefault` — `true` if the column has a `DEFAULT` clause or is
  an identity column. Drives whether the column is required or
  optional in `Table.insert(...)`.
- `isGenerated` — `true` for `GENERATED ... STORED` columns. Such
  columns cannot be inserted; they're absent from the insert attrs
  type entirely.

## Foreign keys

When a table has foreign-key constraints, `tenon-generate` emits
them as a fourth argument to `defineTable`:

```ts
export const posts = defineTable(
  "public",
  "posts",
  {
    id: columnType<number, "int4">({ ... }),
    author_id: columnType<number, "int4">({ ... }),
  },
  [
    {
      name: "posts_author_id_fkey",
      columns: ["author_id"],
      referencedSchema: "public",
      referencedTable: "users",
      referencedColumns: ["id"],
    },
  ],
);
```

The fluent layer reads this metadata to infer the `ON` predicate
when `innerJoin(...)` is called without `.on(...)`. See
[joins](joins.md#fk-inferred-on-predicates) for the call-site
behaviour.

Two notes on what `tenon-generate` emits:

- **Composite FKs are dropped** with a generated comment.
  Single-column FK inference is the v1 surface; multi-column
  FKs aren't yet supported by the type-level matcher.
- **Cross-schema FKs are recorded as-is.** The `referencedSchema`
  is whatever Postgres reports, even when that schema isn't in
  your `--schemas` list. The Table value for the referenced side
  still has to exist in your generated code for inference to
  fire, but the FK record is faithful to the catalog.

## Type mapping

Most Postgres types map straightforwardly: `int4` to `number`,
`text` to `string`, `bool` to `boolean`, `timestamptz` to `Date`.
A few don't:

- `int8` and `numeric` come back as `string`. JavaScript `number`
  cannot losslessly represent integers past 2^53, and `numeric` is
  arbitrary precision.
- `timestamp` (without time zone) comes back as `string`. A
  JavaScript `Date` is always a UTC instant; that would be a lie
  for a tz-less timestamp. Use `timestamptz` if you can.
- Custom types (enums, PostGIS, hstore, ...) fall back to `string`
  with a `// unknown Postgres type "..."` comment in the generated
  file.

The full table is in the [type mapping guide](type-mapping.md).

## When to regenerate

After every database migration. `tenon-generate` is idempotent —
running it again produces the same output if nothing has changed.
A common pattern is a script in `package.json`:

```json
{
  "scripts": {
    "schema:generate": "tenon-generate --database-url $DATABASE_URL --output src/schema.ts"
  }
}
```

Wire it into your migration tooling so the generated file lands in
the same commit as the migration that motivated it. The schema
file is the contract between the database and your TypeScript code;
keep them in lockstep.

## Don't edit the output

The first line of every generated file says so. tenon doesn't
parse the file back; whatever you change will be silently
overwritten on the next regeneration. If you need behaviour the
generator doesn't support (custom column types, projections,
view-as-table treatment), open an issue or work around it in your
own code rather than editing the output.
